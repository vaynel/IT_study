# 무중단 배포 (Zero-Downtime Deployment)

> [!abstract] 개요
> 새로운 버전의 애플리케이션을 배포할 때, 서비스 중단(Downtime) 시간 없이 클라이언트의 요청을 매끄럽게 신규 버전으로 전환하는 전략입니다.

## 1. 주요 배포 전략

### 1.1. 롤링 배포 (Rolling Update)
여러 대의 서버 중 일부를 순차적으로 신규 버전으로 업데이트합니다.
- **장점:** 추가적인 인프라 자원이 크게 필요하지 않음.
- **단점:** 배포 중 구버전과 신버전이 공존하여 호환성 문제가 발생할 수 있음.

### 1.2. 블루/그린 배포 (Blue/Green)
현재 운영 중인 환경(Blue)과 완벽히 동일한 신규 환경(Green)을 구축한 뒤, 로드밸런서의 타겟을 한 번에 Green으로 전환합니다.
- **장점:** 전환 속도가 매우 빠르며, 문제 발생 시 즉시 이전 버전으로 롤백이 가능함.
- **단점:** 서버 자원이 일시적으로 정확히 2배로 필요함.

### 1.3. 카나리 배포 (Canary Release)
신버전을 소수의 사용자(예: 5%)에게만 먼저 배포하여 에러 및 성능을 검증한 뒤, 점진적으로 100%까지 트래픽을 늘립니다.
- **장점:** 장애의 영향 범위를 최소화할 수 있으며, 실제 프로덕션 환경에서 [[01_AB테스트]]와 유사한 검증이 가능함.

## 2. 네트워크 계층 관점 (OSI 7 Layer)

- **L7 (응용 계층):** 무중단 배포의 핵심은 L7 계층의 프록시나 API 게이트웨이에서 라우팅 룰을 동적으로 변경하는 것입니다. 블루/그린 전환 시 Nginx의 upstream 블록을 변경하거나, 카나리 배포 시 HTTP 헤더 값 또는 가중치(Weight)를 기반으로 트래픽을 세밀하게 분할합니다.

## 3. 구현 도구 및 서비스

| 구분 | 오픈소스 (직접 구축) | 상용 / 클라우드 서비스 |
| :--- | :--- | :--- |
| **CI/CD 파이프라인** | Jenkins, GitLab CI | GitHub Actions, AWS CodePipeline |
| **K8s 배포 컨트롤러** | ArgoCD, Flux, Spinnaker | AWS EKS Managed Node, GCP GKE |
| **트래픽 라우팅** | Nginx, Istio, Traefik | AWS CodeDeploy (ALB 연동) |

## 4. 실제 적용 예시

> [!example] 카카오톡 메신저 송금 서버 업데이트 (Blue/Green)
> 1. 기존 송금 API 서버 10대(Blue)가 실시간으로 결제 트래픽을 처리하고 있습니다.
> 2. CI/CD 파이프라인이 최신 코드가 적용된 신규 서버 10대(Green)를 별도로 프로비저닝합니다.
> 3. Green 환경에 내부 테스트 트래픽만 흘려보내 정상 작동을 확인합니다.
> 4. Nginx 기반의 L7 로드밸런서 설정을 변경하여 1초 이내에 모든 사용자의 트래픽을 Green으로 넘깁니다.
> 5. 모니터링 중 치명적인 결함이 발견되면 즉시 Blue로 트래픽을 되돌려(Rollback) 고객 불만을 차단합니다.
