# 무중단 배포 (Zero Downtime Deployment)

## 왜 필요한가?

서비스를 업데이트할 때 **서버를 내렸다 올리면 그 사이 요청이 실패**한다.
무중단 배포는 사용자가 느끼지 못하게 버전을 교체하는 전략이다.

---

## 배포 전략 비교

| 전략 | 방식 | 롤백 속도 | 리소스 | 위험도 |
|------|------|----------|--------|--------|
| Rolling | 순차적 교체 | 느림 | 동일 | 중간 |
| Blue-Green | 통째로 교체 | 빠름 | 2배 | 낮음 |
| Canary | 일부만 먼저 | 중간 | 약간 추가 | 낮음 |

---

## Rolling 배포

서버를 **한 대씩 순서대로** 새 버전으로 교체.

```
초기:    [v1] [v1] [v1] [v1]
1단계:   [v2] [v1] [v1] [v1]
2단계:   [v2] [v2] [v1] [v1]
3단계:   [v2] [v2] [v2] [v1]
완료:    [v2] [v2] [v2] [v2]
```

- **장점**: 추가 리소스 불필요
- **단점**: 배포 중 v1/v2 혼재 → API 하위 호환성 필수

---

## Blue-Green 배포

현재 운영 환경(Blue)과 동일한 새 환경(Green)을 **별도로 준비**한 후 LB에서 한 번에 전환.

```
       ┌─── [Blue - v1]  ← 기존 운영
LB ────┤
       └─── [Green - v2] ← 배포 준비 완료

→ LB 전환 →

       ┌─── [Blue - v1]  ← 대기 (롤백 대기)
LB ────┤
       └─── [Green - v2] ← 신규 운영
```

- **장점**: 롤백 = LB 다시 전환 (빠름), v1/v2 혼재 없음
- **단점**: 리소스 2배 필요, DB 마이그레이션 주의

---

## Canary 배포

새 버전을 **일부 트래픽에만 먼저** 노출하고, 이상 없으면 점차 확대.

```
트래픽의 5%  → [v2 - canary]
트래픽의 95% → [v1 - stable]

→ 문제 없음 확인 후 →

트래픽의 100% → [v2]
```

- **장점**: 실사용자로 검증, 위험 최소화
- **단점**: 모니터링 체계 필수, 배포 기간 길어짐

---

## Kubernetes에서의 무중단 배포

### Rolling Update (기본값)
```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0   # 항상 전체 가용
    maxSurge: 1         # 한 번에 1개씩 추가
```

### Blue-Green (수동 전환)
```bash
# Green 배포 후 Service selector 변경
kubectl patch service myapp -p '{"spec":{"selector":{"version":"green"}}}'
```

---

## DB 마이그레이션 주의사항

배포 중 v1/v2가 동시에 DB를 사용하므로 **하위 호환성** 있게 마이그레이션해야 함.

```
잘못된 순서: 컬럼 삭제 → 앱 배포  (v1이 삭제된 컬럼 사용 → 에러)
올바른 순서:
  1. 새 컬럼 추가 (nullable)
  2. 앱 배포 (v2는 새 컬럼 사용, v1은 무시)
  3. 데이터 마이그레이션
  4. 이전 컬럼 제거
```
