# A/B 테스트

## 개념

두 가지 버전(A, B)을 **실제 사용자에게 동시에 노출**하여 어느 쪽이 더 나은지 데이터로 검증하는 방법.
배포와 결합하면 새 기능의 **위험을 최소화**하면서 점진적으로 롤아웃할 수 있다.

---

## 배포 관점에서의 A/B 테스트

```
전체 트래픽
    ├── 10% → 신규 버전 (B)   ← 지표 모니터링
    └── 90% → 기존 버전 (A)
```

- 문제 없으면 B의 비율을 점진적으로 높임
- 이상 감지 시 즉시 100% A로 롤백

---

## 카나리 배포와의 차이

| 구분 | A/B 테스트 | 카나리 배포 |
|------|-----------|------------|
| 목적 | 기능 효과 검증 (UX, 전환율 등) | 안정성 검증 (에러율, 성능) |
| 기간 | 비교적 장기 (통계 유의성 확보) | 단기 (이상 없으면 바로 전체 배포) |
| 대상 선택 | 랜덤 or 특정 세그먼트 | 일부 트래픽 |

---

## 피처 플래그 (Feature Flag)

코드를 배포하되, 기능을 **런타임에 on/off** 할 수 있게 하는 방식.
A/B 테스트와 결합하면 재배포 없이 실험 가능.

```python
# 예시
if feature_flag("new_checkout_flow", user_id):
    return new_checkout()
else:
    return old_checkout()
```

### 피처 플래그 도구
- **오픈소스**: Unleash, Flagsmith, OpenFeature
- **클라우드**: AWS AppConfig, LaunchDarkly

## 트래픽 분할 방법

### Nginx 가중치 기반
```nginx
upstream ab_test {
    server v1.internal weight=9;  # 90%
    server v2.internal weight=1;  # 10%
}
```

### Cookie / Header 기반 (L7)
```nginx
map $cookie_variant $upstream {
    "B" v2_backend;
    default v1_backend;
}
```

## 통계적 유의성

A/B 테스트 결과가 **우연이 아님을 보장**하려면 충분한 샘플이 필요함.

- p-value < 0.05 → 95% 신뢰 수준
- 샘플이 적으면 결과 신뢰 불가 → 성급한 결론 금지
- 도구: Google Optimize, Statsig, 자체 구현
